# Sprint 11c — durable AI training plans (backend)

This is the historical substage report. The completed host/UI integration and coordinator fixes are recorded in [Stage 11 acceptance](stage-11-acceptance.md).

The AI training-plan backend is complete and deterministically tested; no UI or controller is wired to it yet. `prepare` builds one account's plan input for **free** and stores it durably: the bounded real candidate pool of the account's own source instance, the aggregate weakness report, the identifier-free 11a ability aggregate, the settings revision it borrowed and the semantic evidence hash. Nothing is dispatched, nothing is charged, and re-preparing the same request id with the same account, settings and candidate scope is an idempotent replay; a different account, plan settings or candidate scope under the same id is a typed `request_conflict`.

`run` is the one explicit, paid call. A run of an id that was never prepared refuses with `preparation_missing` before any write, a run of an already `reserved`/`settled`/`uncertain`/`cancelled` attempt returns that attempt's own durable audit and never dispatches twice, and exactly one transaction reserves the call: it recovers expired reservations, re-reads the stored settings (revision, provider and analysis model must still match the preparation), enforces the plugin-wide single flight and the rolling quota, re-validates the whole preparation against the current store, writes the `reserved` row and finally re-checks cancellation before any provider IO. A cancellation inside that transaction rolls the reservation back for free; a cancellation between the reservation commit and the dispatch closes it with known-zero usage, while a cancellation during settlement keeps the already-paid usage and discards the plan (see "Cancellation-safe settlement" below).

## Candidate scope

`PlanPrepareRequest.candidateProblemKeys` is an optional explicit selection. When present, **only** those stored problems of the account's own source instance may enter the pool: a key that is not canonical, a repeated key or more than 100 keys is bad input; an unknown key is `missing_reference`; a key of another source instance is refused with `candidate_source_mismatch`; and a selected problem the account already accepted is excluded and counted in the exclusions instead of being replaced by another candidate. An explicit empty list is an honest `preparation_empty` refusal, never a silent fallback to the automatic pool, and a `candidateLimit` below the selection is a typed conflict rather than a truncation. The requested scope is stored on the preparation and covered by the evidence hash, so the same request id cannot name a different scope. Without `candidateProblemKeys` the automatic bounded pool is unchanged.

## Truthful accounting and cost

Every settled row records known usage. A provider that never reported usage produces `uncertain` with `null` usage: the call keeps its quota slot and is never retried automatically, because a free retry would fabricate a cost the provider may already have charged. A model answer that fails domain validation settles with its retained cost and `invalid_output` and is never repaired. The settlement shape is validated directly: a `settled` row has known usage and exactly one of a stored plan (`planId` and `planHash` together) or a typed error — both or neither is refused. Terminal rows are immutable, an identical duplicate save is a no-op, and usage survives a SQLite reopen.

The planning quota is an independent counter of planning attempts (`reserved`, `settled`, `uncertain`) over a plugin-wide rolling 24 hours. It **borrows the coaching cap value** — `settings.coaching.maxCallsPer24Hours` (default 10) — and the analysis role's model, output cap and the global request timeout; 11c deliberately adds no settings field. Planning calls always run at the approved `max` effort with the default provider `deepseek-official` and the default analysis model `deepseek-flash`, but nothing is dispatched until a caller explicitly runs a preparation.

## Freshness and revalidation

The preparation is re-proved against the current store immediately before dispatch and again after the model answers. The ability assessment is recomputed at the **current injected instant**, not at the preparation instant: the identifier-free aggregate carries no observation timestamp, so a moved clock alone does not make it differ, while a submission or retrospective recorded after the preparation on a previously attempted, non-candidate problem (for example its first AC) does change it and produces a typed `stale_preparation` refusal. Evidence that genuinely aged out of the rolling 90-day window is a real change and is not ignored. A change that lands while the model is answering settles the attempt with its retained cost and stores no plan.

## Cancellation-safe settlement (repair 2)

The provider dispatch stays cancellable, but the settlement of an already-paid call is not: the post-provider re-validation and the plan write run under an internal non-cancellable token, and the caller's token is only **sampled** — before the plan write and after each charged write. A cancellation observed at one of those samples aborts the settlement transaction with a private sentinel, so the plan and any partial settlement roll back together, and a **new** transaction re-records the already-known usage and host correlation with a `cancelled` error and no plan. A known cost is never converted into zero or unknown, and a terminal row is never rewritten or refunded; a cancellation that lands after the settlement commit leaves the stored record exactly as committed. The same rollback path serves an unexpected exception from the post-provider re-validation or the plan write, which is settled with a fixed sanitized `provider_error` that says to prepare again (the raw value only reaches the optional local diagnostic hook). The fallback settlement re-reads the durable attempt first, so a late settlement is idempotent against a terminal row, a vanished or non-reserved row is a typed `storage_inconsistent` instead of a fabricated record, and an unavailable store surfaces its own failure while the reservation stays visible. A separate post-dispatch guard re-reads the stored workbench settings revision, provider and analysis model before the plan write and withholds the plan with a fixed sanitized message when they moved, so a plan can never be stored under a configuration the call was not reserved under.

## Recovery, history and storage

Recovery converts every expired `reserved` attempt to `uncertain` and reports the number it actually converted; still-live reservations are preserved exactly, keep their quota slots and remain the single-flight blocker. `history` is a bounded, account-scoped, newest-first read of metadata-only attempt views (at most 50 rows) that carries no input hash, preparation, candidate tags or error body, so a refreshed page can recover the attempts it no longer holds in memory without turning a history read into a spoiler dump. `cancel` of a still-`prepared` attempt is free, terminal and never counted as a used call.

Planning attempts live in the new schema-v4 `plan_attempts` table. A recognized v3 (and v2/v1) database is copied consistently before migration, the migration only adds tables, every existing row is retained, and the historical schema helpers keep writing their own literal versions. Both the row body and its nested preparation (including the requested candidate scope) are strictly re-validated on read, so a hand-edited row is `corrupt_row` instead of a cast.

## Pending 11d integration

This stage ships the backend only. Stage 11d still owns: the reciprocal shared-start gate with batch, coaching and settings including the persisted reservation checks; startup recovery/disposal and background token handling through ModelOperations; the typed business API validation, routes and projections; and all UI defaults, history rendering, reveal handling and the controller wiring. The backend today does **not** check batch or coaching activity directly, and because the UI is not wired there is no current default AI behaviour: every paid call still requires an explicit run of a durable preparation.
