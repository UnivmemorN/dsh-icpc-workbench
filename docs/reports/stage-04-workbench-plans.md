- Weakness: one bounded submission walk per operation (500-row pages, refuses >50 000 rows or >20 000 distinct problems), decisions read per attempted problem with its stored head (50 000-row bound) so only current AI decisions count, retrospectives bounded at 50 000. Missing metadata for a same-source valid ref still counts as attempted, a same-source retrospective without a submission stays valid history, and a problem in another subdomain of the same instance stays valid evidence. The 50 000-before-yield bound, one walk per operation and the no-per-row-lookup behaviour are unchanged. No schema/adapter/pipeline/API/UI change.
- Preview: ≤500 distinct stored candidate keys of the account's own source, real title/URL/ref from the store, current effective tags after the stale filter, local candidate/plan ids, `generateRulePlan` only (no model). Settings defaults 7 days / 60 min / 30 min estimate, bounds 1..30 / 1..480. Draft stored in one transaction; the preview DTO carries the full sha256 of the stored plan as its CAS token; account + token re-checked before the write; empty pool returns domain `insufficient_evidence` plus real starter recommendations and stores nothing.
- Plans: list/get bound to the real account. Every unsolved task omits `taxonomyIds` and `rationale` (absent own properties, also in JSON), `targetedTagIds` exists only under explicit `reveal`; aggregate `evidence.sufficientTagIds` stays visible. Adopt/edit/check-off re-read the stored plan and compare `expectedHash` inside the transaction, then transition and save; a stale hash is `invalid_transition`/`stale_plan_hash` with no write. Task edits accept only `day`/`minutes`/`kind`; domain bounds, overfill and task-state rules are preserved; check-off is a user record and creates no submission. Every mutation returns the fresh projected plan and its new hash.
